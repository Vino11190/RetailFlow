
# RetailFlow — Surrogate Keys and SCD Type 2 Design

## 1. Purpose

Define the warehouse key strategy and historical dimension
management rules for RetailFlow's Gold analytical layer.

## 2. Surrogate Key Strategy

- dim_customer: BIGINT GENERATED BY DEFAULT AS IDENTITY
- dim_product: BIGINT GENERATED BY DEFAULT AS IDENTITY
- dim_store: BIGINT GENERATED BY DEFAULT AS IDENTITY
- dim_supplier: BIGINT GENERATED BY DEFAULT AS IDENTITY
- dim_channel: BIGINT GENERATED BY DEFAULT AS IDENTITY
- dim_date: INTEGER YYYYMMDD

Reserve key 0 for unknown/not-applicable dimension members.

Natural business keys must be retained in dimensions.

Fact tables reference surrogate dimension keys through
foreign-key constraints.

## 3. Product SCD Type 2

Business key: product_id
Surrogate key: product_key

Tracked attributes:
- sku
- product_name
- category_id
- category_name
- brand
- unit_price
- currency
- active

Version metadata:
- effective_from TIMESTAMPTZ NOT NULL
- effective_to TIMESTAMPTZ NULL
- is_current BOOLEAN NOT NULL
- attribute_hash CHAR(64) NOT NULL

## 4. Change Detection

1. Read and validate the incoming product record.
2. Normalize tracked attributes.
3. Calculate a deterministic SHA-256 attribute hash.
4. Find the current version for product_id.
5. If no current version exists, insert a new version.
6. If the hash is unchanged, retain the existing version.
7. If the hash differs:
   a. Close the existing version at the observed change time.
   b. Set its is_current flag to false.
   c. Insert the new version using a new surrogate key.
8. Commit the change atomically.

## 5. Effective Dating

Validity intervals are half-open:

effective_from <= event_timestamp < effective_to

For current records:
- effective_to IS NULL
- is_current = TRUE

Only one current version may exist per product_id.

Historical versions must not overlap.

## 6. Historical Fact Lookup

Facts should reference the product version valid at the
business event timestamp.

If the event predates the earliest known product version,
do not invent a historical version.

Use a documented fallback policy, such as unknown product,
and flag the record for investigation.

If source timestamps cannot be parsed, quarantine the
affected record rather than assigning an invented date.

## 7. Idempotency

Reprocessing identical product attributes must not create
another SCD version.

A repeated batch must produce the same business result.

Use transactions, uniqueness constraints and controlled
change detection.

## 8. Customer Dimension

Initial design: Type 1, with privacy-aware attributes.

Potentially sensitive fields should not be exposed in
general-purpose analytical reporting.

Historical customer attribute tracking is not enabled
unless justified by a reporting requirement.

## 9. Other Dimensions

dim_store: Type 1
dim_supplier: Type 1
dim_channel: Type 1
dim_date: Static

## 10. Validation Requirements

- One current product version per business key.
- No overlapping effective-date intervals.
- Unique surrogate keys.
- Deterministic change detection.
- Idempotent reprocessing.
- Historical facts resolve to the correct version.
- Unknown dimension members are present.
- No fabricated source history.
